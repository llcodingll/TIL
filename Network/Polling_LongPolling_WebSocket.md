## Polling vs Long Polling vs WebSocket

---
### Polling


: 클라이언트가 일정 간격으로 서버에 요청 -> 새로운 알림 있는지 확인
- 장점
  - 구현 간단, HTTP 기반 = 기존 시스템에 쉽게 추가 가능
  - 브라우저/다양한 클라이언트 환경에서 안정적으로 동작
- 단점
  - 클라이언트에서 주기적 요청 필요 = 서버와 네트워크 부하 증가
  - 실시간성 감소
---
### Long Polling


: 클라이언트가 서버에 요청 -> 새로운 알림 발생 시까지 응답 지연
- 장점
  - Polling 대비 부하 감소
  - 알림 발생 시, 즉시 전달 가능 = 실시간성 향상
- 단점
  - 서버 연결 유지로 특정 조건에서 자원 과다 사용
  - 연결 끊기면 재연결하는 로직 작성 필요
---
### WebSocket


: 클라이언트, 서버 `양방향 연결`, 서버에서 클라이언트로 직접 메시지 push
- 장점
  - 완전 실시간
  - Long Polling 대비 서버 부하 감소, 네트워크 사용량 감소
- 단점
  - 구현 복잡, HTTP 기반 아닌 WebSocket은 지원하지 않는 환경에서는 동작 불가
  - 서버 리소스(특히 연결수) 증가
---
#### 덧붙이기
- Repick 프로젝트에서는 알림을 구현하기 위해 통신 방법을 알아보았음.
- 알림은 `양방향`이 아니기 때문에 WebSocket은 실시간성을 띄더라도 다른 대안을 찾을 수 있을 것이라 생각해 기각.
- 이미 Kafka를 사용하고 있었기 때문에 Polling보다는 부하가 적고 Polling보다는 실시간성을 띌 수 있는 Long Polling을 선택해 Kafka와 함께 사용하기로 결정.
---
##### 구현 로직
1. 댓글 서버에서 댓글 작성 시 Kafka에 이벤트를 발행.
2. 게시글 서버가 Kafka의 메시지를 소비하여 알림 데이터를 생성.
3. 게시글 서버는 Long Polling으로 클라이언트에게 알림 전송.

---
### 회고 중 발견한 아쉬운 점
개발 당시에는 kafka가 이미 서버에 구현되어있고 그래서 이를 최대한 활용해서 long polling이 가장 적합하다고 생각해 구현했음.

근데 이후에 회고하면서 생각해보니 웹소켓이 양방향이라 못 쓴 거라면 sse를 쓰는 것이 long polling의 상위호환 버전이라 그렇게 개선할 수 있겠다 싶어 아쉬움.
